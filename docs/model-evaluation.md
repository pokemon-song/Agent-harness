# 不同大模型的闭环评测与评分协议

本协议比较不同模型接入**同一套 Go2 MuJoCo Harness**后的任务表现。机器人、场景、感知、工具、控制器、评分条件和预算保持一致，只更换模型及其服务配置。结果代表“模型＋当前适配器＋本 Harness”的整套闭环，不代表裸模型的通用智能，也不是 QUARD 原始环境或论文成绩的复现。

机器人适配架构改造后，新计划额外冻结完整 `RobotProfile` 及其摘要，源码指纹递归覆盖机器人、环境和评估模块；每回合保存 `robot_profile.json`、实际工具及绑定机器人身份的提示词。评分权重不变，但新旧协议摘要不同，须新建计划，不能续跑旧计划或混排。旧归档仍能离线评分。新增 `model_wait_s`、`action_execution_wall_s` 为诊断时间，不改变原五维公式；具体边界见 [机器人适配架构](robot-architecture.md)。

仿真沿用 `paused_during_model_inference`：等待模型时物理世界暂停，执行动作时继续推进。模型延迟影响墙钟预算，但不会让机器人在 API 等待期间自行走动。因此不能把成绩解释为真实机器人实时控制能力。

既有v2真实思考API评测已经保存：DeepSeek完成65回合，严格成功60次，综合分82.96；Qwen因账号服务阻塞保留阶段记录，不能形成完整跨模型排名，见 [原阶段报告](../runs/model-eval/20261103-deepseek-flash-vs-qwen-max/REPORT.zh-CN.md)。本次新增复合任务与v3只做不调用付费模型API的实现及可达性验证，尚无v3模型成绩。下文的 `run` 命令会调用配置的模型服务。

新建计划**默认仍为 `go2-model-eval-v2`**，13任务×5次＝65回合、四类各25%。显式选择 **`go2-model-eval-v3`** 后加入本地复合类，14任务×5次＝70回合、五类各20%；每回合的五维分项与预算相同。旧 `go2-model-eval-v1` 计划仍可离线报告和比较，继续使用原来的四类等权严格成功率分。不同版本不得混排；新增v3不会改写已有v2计划、82.96分或原报告。

## 1. 固定评测范围

默认v2评测使用现有 `quard-planar` 中13个可运行场景。每场景运行5次，共 **65个 episode／模型**。

| 组别 | 场景 | 每组 episode 数 | 组间权重 |
| --- | --- | ---: | ---: |
| `go_to` | `go_to_blue_ball`、`go_to_green_cube`、`go_to_red_cube` | 15 | 25% |
| `distinguish` | `distinguish_texture_a`、`distinguish_texture_b`、`distinguish_texture_c` | 15 | 25% |
| `go_avoid` | `go_avoid_texture_cooker`、`go_avoid_texture_drawers`、`go_avoid_texture_fan`、`go_avoid_texture_sofa` | 20 | 25% |
| `go_through` | `go_through_green_rectangle_tunnel`、`go_through_red_triangle_tunnel`、`go_through_yellow_triangle_tunnel` | 15 | 25% |

### 1.1 显式v3：增加复合类

`plan --protocol go2-model-eval-v3` 在原13项上增加 `composite_drawers_gate_b`，类别为 `composite`，要求依次绕抽屉柜、穿绿色矩形门、从A/B/C中接近B并停稳。该场景是本地自建复合任务，不是QUARD官方任务。

| v3组别 | 场景数 | episode数 | 组间权重 |
| --- | ---: | ---: | ---: |
| `go_to` | 3 | 15 | 20% |
| `distinguish` | 3 | 15 | 20% |
| `go_avoid` | 4 | 20 | 20% |
| `go_through` | 3 | 15 | 20% |
| `composite` | 1 | 5 | 20% |
| 合计 | 14 | 70 | 100% |

复合类只有1项任务、5次重复，类别权重仍为20%；这是预先确定的类别等权，不是把70回合直接微平均。场景定义、清单与运行命令见 [复合测试说明](composite-tests.md)，清单见 [datasets/composite/dataset.json](../datasets/composite/dataset.json)。实际仿真从 `scenarios.py` 加载，模型不会直接读取清单中的目标真值。

`red_marker` 是开发与回归场景，不进入主分。`crawl_red_gate2`、`crawl_red_gate3` 当前底层不支持，也不进入分母；不能把它们记作模型成功或失败。

静止高度／仰角控制另设后续专项。当前导航及复合任务未要求到达指定姿态并独立验收，不能据这些回合宣称已比较静止调姿能力，更不能宣称测过保持低姿态行走或爬行。公开工具中的姿态接口仍对所有模型一致，模型调用它也不会获得额外姿态分。

场景定义见 [scenarios.py](../go2_demo/scenarios.py)，当前任务语义和场景边界见 [scenarios.md](scenarios.md)。

## 2. 场景种子、重复与公平条件

标准计划固定 `scene_seed=0`。v2原13项和v3新增复合任务的 `target_jitter_m` 均为0，因此5次repeat使用同样的场景，主要观察模型输出和服务的重复运行波动，**不是5个新场景实例**。当前 `--seed` 也没有设置模型服务的采样随机种子，不能据此承诺模型输出确定。

每个 episode 都重新创建仿真、模型适配器、跟踪器和近期历史，不共享上一回合的历史或外部记忆。对各模型保持以下条件一致：

- 任务文本、系统提示、工具 schema、观测与动作协议、完成条件；
- 场景、初始状态、RGB尺寸、相机标定、几何跟踪算法及模型可见信息；
- 机器人资产、预训练步态、姿态控制器、限幅、停止条件与物理参数；
- 代码版本、资产校验记录、依赖环境和仿真暂停方式；
- 预算、近期历史长度、当前图像窗口和错误反馈规则。

各模型应使用同一配对场景与重复编号；运行顺序可交错安排，减小时段、服务负载和网络波动造成的影响。模型做出不同动作后，后续画面和轨迹自然会分叉，不应强行回放成相同观测。

调提示、换工具、增预算或更换控制器后，应建立新的协议版本与结果组，不能继续混入原组排名。模型名称、服务配置和采样参数须明确记录；相同的输出 token 上限不表示不同服务商使用了相同计算量。

程序记录请求模型名、provider，以及事件中实际返回的模型标识；API采样参数目前使用服务默认值，没有强行设置 temperature、top_p 或采样seed。服务地址、部署版本和服务端默认值需随实验另行记录，不含密钥。协议指纹不能自动验证供应商内部版本或默认值没有改变，使用滚动模型别名时尤其需要人工核对。

## 3. 固定每回合预算

| 参数 | 标准值 |
| --- | ---: |
| 最大模型调用次数 | 30 |
| 最大墙钟时间 | 300秒 |
| 最大仿真时间 | 120秒 |
| 保留近期完整工具轮次 | 6 |
| 每次请求输出 token 上限 | 8192，包含思考 |
| 单次 API 超时 | 90秒，同时受剩余墙钟预算约束 |
| 思考语义 | 开启，由provider转换为对应请求字段 |

现有适配器使用非流式Chat Completions，需要模型服务支持图片和工具调用。DeepSeek请求 `thinking={"type":"enabled"}`；Qwen请求 `enable_thinking=true`、`preserve_thinking=true`，使用 `max_completion_tokens` 限制思考与回答的总输出。`compatible` 不能理解为所有厂商原生推理协议都已适配；必须记录兼容情况及API／协议错误，不能直接解释为模型不理解任务。

墙钟时间包含 episode 内的模型请求、仿真执行和日志等开销，仿真时间单独统计。最终停止也会推进仿真；`finish` 后如果最终停止使预算超限，仍按运行器的最终结果处理。运行器不会自动重试真实 API 请求；操作人员也不能在看过结果后只补跑失败样本、保留其中最好的一次。

## 4. 每个 episode 的严格成功

成功沿用 [runner.py](../go2_demo/runner.py) 与 [backend.py](../go2_demo/backend.py) 的现有判定，不放宽阈值、不另造替代成功标准。一个有效 episode 只有同时满足下列条件，严格成功指示才记 `S=1`：

1. 正常以 `finish` 声明结束；
2. 独立评测器确认该场景目标达成；
3. 最终停止得到确认；
4. 整个 episode 没有累计环境碰撞或跌倒；
5. 未超过模型调用、墙钟和仿真预算。

其他有效完成结果均记 `S=0`，该回合所有得分均为0。工具返回 `finish: succeeded` 仅表示声明被记录，不能替代最终 `metrics.success`。独立几何条件已合格、但模型没有及时调用 `finish`，也不算成功。

### 4.1 接近目标、字母辨别和绕障

在正确目标中心的水平距离 `1.0±0.18 m` 内，朝向误差不超过 `0.25 rad`；水平速度小于 `0.12 m/s`、偏航角速度小于 `0.25 rad/s`，并满足无碰撞、无跌倒和预算条件。

选错物体或字母不能因为停止或声明完成而得分。绕障与普通接近任务共享最终到达条件，但沿途碰撞记录会使整个回合失败。

### 4.2 穿门

独立轨迹必须显示 `base` 参考点从开口内部向前跨越门框平面，随后 `base` 到达门后至少0.8米的区域，再停稳并正常完成。

这里验收的是当前实现的 **base轨迹＋碰撞／跌倒记录**，没有单独验证完整机器人包络、整机扫掠净空或全身离开出口。门后参照标记的1米距离及朝向误差不是穿门成功条件，不能拿接近目标的距离阈值给穿门重新打分。

### 4.3 v3复合任务

独立轨迹必须存在“先到抽屉柜后方→从绿色矩形门开口向前跨越→继续到门后至少0.8米”的正确顺序链。终态仍须在门后完成区域，并满足正确B中心的水平距离 `1.0±0.18 m`、朝向误差≤`0.25 rad`、速度<`0.12 m/s`、偏航角速度绝对值<`0.25 rad/s`，以及全程无碰撞／跌倒、未超预算、正常 `finish` 与最终停稳。

`stages={avoid_drawers,pass_gate,approach_b}` 与 `stage_completion_rate=sum(stages)/3` 只作诊断。仅完成某阶段不算严格成功，不增加部分主分；阶段全部达成也须通过顺序和全局条件。模型可回退重试，只要轨迹中存在正确事件链且最终合格；完整机器人包络的边界与穿门任务相同。详细几何条件见 [复合测试说明](composite-tests.md)。

## 5. v2／v3主分：严格成功门控的五维综合分

### 5.1 每回合公式与固定权重

```text
clip(x) = min(1, max(0, x))
P = min(1, D_lb / L)
W = clip(1 - wall_elapsed_s / 300)
T = clip(1 - sim_elapsed_s / 120)
C = clip((30 - model_calls) / 29)

回合综合分 = S × (60 + 20P + 10W + 5T + 5C)
```

`L` 是实际水平路径长度，`D_lb` 是该任务固定的几何直线距离下界，单位均为米。若 `L=0` 且 `D_lb>0`，`P=0`；两者均为0时 `P=1`。每个归一化效率量都限制在0到1之间。

| 维度 | 每回合得分 | 满分 | 含义 |
| --- | ---: | ---: | --- |
| 严格成功 | `60S` | 60 | 完成目标、停稳、安全且未超预算 |
| 路径效率 | `20SP` | 20 | 实际路径相对固定几何下界的效率 |
| 墙钟效率 | `10SW` | 10 | 相对300秒预算节省的时间 |
| 仿真效率 | `5ST` | 5 | 相对120秒预算节省的仿真时间 |
| 调用效率 | `5SC` | 5 | 1次调用对应1，30次调用对应0 |

有效失败的 `S=0`，即使早停、没有移动、调用少，也不能获得效率奖励。成功回合的基础分为60分，其余40分衡量效率；这些权重在运行前冻结。**综合分优先的排名允许成功率略低、效率更高的模型排在前面**，因此必须同时报告严格成功率，不能把综合分称为成功率或声称排名始终优先保证成功率。

### 5.2 路径测量与几何下界

路径长度来自 `trajectory.jsonl` 中约50Hz采样的 `base` 水平位置，以新 `episode_start` 事件中的精确初始 `xy` 为起点，累加相邻点的二维欧氏距离：

```text
L = Σ sqrt((x_i - x_(i-1))² + (y_i - y_(i-1))²)

接近／辨别／绕障／复合任务的最终B停靠：
D_lb = max(0, dist_xy(start, correct_target) - (standoff_m + 0.18))

穿门：
D_lb = max(0, finish_x_min_m - start_x)
```

`start` 是本回合开始时的真实位置，`correct_target` 是独立评分所用的正确目标中心；这些真值只用于离线评分，不作为额外观测提供给模型。目标接近任务的 `0.18 m` 是当前固定成功距离容差。穿门的下界只使用到门后完成区域所需的前向位移，跨越门框开口仍须满足第4节的独立成功判定。

复合任务的路径参照仍是起点到最终B停靠区域的直线距离下界，不把柜后和门框中间约束相加为一条“最短路径”。中间阶段是否按序达成属于严格成功条件，不能用较高的路径分替代。

该参照是**几何直线距离下界**，忽略障碍、朝向、机器人包络和控制器限制，不是求解出的最短可行路径，也不是SPL。绕障时真正安全的路径可能必然更长，路径维度满分可能不可达；同一任务的参照对所有模型固定一致。不能因为某个模型绕障而事后调整它的下界。

路径统计排除回合开始前的暖机，包含回合内所有停止漂移、`finish` 动作及最终停稳阶段。它统计实际运动，不累加工具请求的距离，也不以起终点直线距离代替实际路径。原地转动没有独立转向加分或扣分，但转动引起的水平漂移仍计入路径。缺失、稀疏、时间逆序或末点与最终状态不匹配的轨迹归为invalid，不能把漏记轨迹当成短路径。

### 5.3 场景、组别与总榜汇总

每个场景先对5次repeat的综合分及五个分项分别取平均，再对组内场景等权平均；最后按协议对类别等权平均，得到总分及各分项总分：

```text
场景综合分 = mean(该场景5个回合的综合分)
组综合分 = mean(组内各场景综合分)
v2总综合分 = (go_to + distinguish + go_avoid + go_through) / 4
v3总综合分 = (go_to + distinguish + go_avoid + go_through + composite) / 5
```

总分范围为0到100，各分项采用完全相同的宏平均顺序，五个分项总分相加等于综合分。v2四组各25%，v3五组各20%，不随组内回合数变化。正式排名按同协议的总综合分降序，同分并列；不以显示时的四舍五入制造名次差异。

严格成功率继续单列，不与效率混成“成功率”：

```text
场景严格成功率 = 成功次数 / 5
组严格成功率 = mean(组内各场景严格成功率)
宏平均严格成功率百分分 = 100 × mean(该协议各组严格成功率)
整体微平均严格成功率 = 所有成功回合数 / 计划回合数（v2为65，v3为70）
```

例如，三个15回合的组全成功、20回合的绕障组全失败时，宏平均严格成功率百分分为75，微平均为 `45/65≈69.23%`；**v2综合分还取决于成功回合的效率，不能直接写成75分**。旧v1协议才以该宏平均严格成功率百分分作为主分。

## 6. 失败、无效结果与未运行

正式报告必须区分“模型闭环失败”和“这次试验没有产生可用结果”。不能通过删行改变分母。

| 状态 | 典型终止类型 | 处理 |
| --- | --- | --- |
| 成功 | `finish` 且最终成功条件全部通过 | 有效结果，`S=1`，按五维公式计分 |
| 有效失败 | `finish` 但独立评分不通过、`abort`、`budget_exhausted`、`execution_failure`；或 `model_error` 且 `error.code` 为 `MODEL_PROTOCOL_ERROR`／`MODEL_TIMEOUT` | 有效结果，`S=0`，五个分项与综合分均为0 |
| `invalid` | `configuration_error`、`startup_error`、`runtime_error`、`evaluation_error`、`logging_error`、`interrupted`；`model_error` 的其他／未知错误代码；或结果损坏／基准协议核查不通过 | 不形成正式主分，单独报告原因 |
| `pending` | 计划中的回合尚未运行，或尚无完整结果 | 不形成正式主分，保留计划槽位 |

`model_error` 不能一概按0计入，必须继续检查 `error.code`。仅当前适配器拒绝返回的 `MODEL_PROTOCOL_ERROR`（含明确响应截断），以及触及固定API时间预算的 `MODEL_TIMEOUT`，按有效失败记0。协议总码不等同于JSON错误；没有raw响应时，通用JSON解析拒绝不能定位到外层响应还是工具参数，更不能进一步归因为规划差。前者不包括基准配置指纹不一致等离线协议核查失败，后者也不意味着已经定位到模型推理能力问题。

HTTP、鉴权、限流、服务端、网络传输、配置及未知代码均保守归为invalid。当前适配器将各HTTP状态统一记为 `MODEL_HTTP_ERROR`，网络传输记为 `MODEL_TRANSPORT_ERROR`，仅凭这些记录无法可靠区分基础设施故障与接口兼容问题，不能把接口不适配称为模型规划差。报告须保存原始终止类型和错误代码，不按排名需要事后改变归因；批次遇到这类连接／服务／兼容性错误时停止后续回合，尚未运行的槽位保持pending。

有 `pending` 或 `invalid` 时，只可给出**临时零填分**：对尚不能记为成功的计划槽位保守填0，并按完整计划分母计算；必须同时显示已完成、有效失败、invalid与pending数，正式分标为不可用。临时分不能用于正式优劣排名。

每个计划槽位对应唯一结果，不允许“取最新成功”“取最高分”“用相同任务另一目录替换失败”。需要重做基础设施故障时，保留原始记录并使用明确的新计划或重跑记录；不能悄悄覆盖原结果。首次启动前冻结的重跑规则才可以对所有模型一致执行。

## 7. 报告展示与旁报指标

综合分之外必须保留原始量，避免相同分数掩盖不同的表现。报告在每回合、每场景、每组与整体层级展示综合分及五个分项，并保留每场景成功次数／5、相应协议各类宏平均严格成功率和整体微平均。复合任务另列阶段完成率作诊断，不加入严格成功次数或分项得分。

| 展示层级 | 必须包含的字段 |
| --- | --- |
| 模型总览／比较表 | 模型标识、协议ID及指纹、正式或临时状态、综合分、五个分项、宏平均严格成功率百分分、微平均成功率、有效／失败／invalid／pending数量 |
| 场景／组别表 | 场景或组名、成功数与计划数、综合分、五个分项、严格成功率 |
| 回合明细 | 唯一case、状态及终止／错误类型、`S`、实际路径米数、固定下界、墙钟秒数、仿真秒数、模型调用数、API延迟、归一化效率与得分、原始文件路径 |
| 原始效率汇总 | 有效试验、成功试验各自的样本数与路径／时间／调用统计；跨模型共同成功case子集的同口径统计 |

报告汇总已完成试验和成功试验的实际路径、调用与耗时；跨模型比较另外给出各模型共同成功的相同case子集效率。不能仅凭全部有效试验的平均耗时宣布某模型更快，因为失败早停也会缩短运行。成功样本和共同成功子集仅用于解释效率，不改变综合分使用的全部计划槽位及分母。

API延迟、token计数、接口校验错误率和累计转向量单列，不再额外加进总分。API延迟已经影响墙钟时间，不重复增加一项延迟惩罚；累计转向量也不等同于水平路径。碰撞、跌倒、超预算、主动放弃、错误完成声明和错误类型分布帮助解释失败。动作派发数、成功／失败执行次数、错误完成声明及感知／控制器错误细分可从原始日志进一步分析，不能把未自动归因的细项冒充已完成统计。

请求有效性与动作执行成功率不同。名称、schema、单轮单工具或调用ID校验失败属于无效请求；控制器未收敛不应一概算成 schema 错误。一个响应含多个请求时，每个请求都要保留，不能只留下执行成功的一项。缓存去重的合法请求也不代表又执行了一次物理动作。现有 `motion_calls`、`posture_calls` 是相应工具的派发计数，不能直接称为实际移动次数或成功动作次数。

效率汇总应注明是否包含有效失败，并保留每回合值。不能只展示最快的成功样本；若单列成功样本效率，必须同时给出其样本数和全部试验结果。所有纳入正式比较的模型应使用一致的机器、渲染方式和运行负载；墙钟分也反映服务延迟及本地执行开销，不能单独解释为模型规划速度。

模型调用次数在请求前增加；某些失败请求可能已产生服务端计算和费用，却没有可用的 usage 返回，或在响应解析失败前尚未记录 usage。因此已知usage之和可能不覆盖失败请求，不能冒充完整总量；缺失 token 应标“未知／不完整”，不能当成0 token或零费用。当前日志仅保留 `prompt_tokens`、`completion_tokens`、`total_tokens`，不保证覆盖厂商全部缓存或推理计费细节。没有可信价格和计费口径时不编造美元费用，也不把不同 tokenizer 的 token 当作等量计算。

当前没有经过验证的最短可行路径真值，**不报告 SPL**；第5节的几何下界路径分不能改称SPL。没有预先标注的不可完成实例，也不把调用 `abort` 算作“正确识别不可完成”的成功。

## 8. 计划、运行、报告与比较

评测入口使用保存的计划绑定模型标签、场景、重复编号、预算、评分权重、路径下界及协议。新计划默认使用v2，增加复合类须显式选择v3，不能看过结果后再调权重或参照。计划中不保存明文密钥；密钥只在实际运行时传入。`plan` 只冻结配置，不联网，也不证明模型服务已经兼容。

```bash
# 1. 为模型A建立标准计划；compatible端点使用既有MODEL_BASE_URL配置
python -m go2_demo.benchmark_cli plan \
  --label model-a --provider compatible --model-name MODEL_A \
  --output-dir runs/model-eval/model-a --repeats 5

# 显式创建v3：14任务×5次，五类各20%；此命令仍不调用API
python -m go2_demo.benchmark_cli plan \
  --protocol go2-model-eval-v3 \
  --label model-a-v3 --provider compatible --model-name MODEL_A \
  --output-dir runs/model-eval/model-a-v3 --repeats 5

# 2. 以后实际运行：该步骤会调用模型API并产生费用
python -m go2_demo.benchmark_cli run \
  --plan runs/model-eval/model-a/plan.json \
  --api-key-file /path/to/model-a.key --no-env-proxy

# 3. 读取已保存的结果离线打分，不再次调用模型
python -m go2_demo.benchmark_cli report \
  --plan runs/model-eval/model-a/plan.json \
  --output runs/model-eval/model-a/report.json

# 4. 为模型B独立建计划和运行后，比较两份计划
python -m go2_demo.benchmark_cli compare \
  --plans runs/model-eval/model-a/plan.json runs/model-eval/model-b/plan.json
```

`model-a`、`MODEL_A` 和密钥路径均为示例。第3步把离线报告保存到该计划目录的 `report.json`；省略 `--output` 时打印JSON，不另发起API请求。不同模型使用各自输出目录与凭据，不复用上一模型的会话历史。`--no-env-proxy` 是服务连接方式，应按实际网络选择并记录；不能因为单个模型网络异常临时改变评分条件。

`report` 应核对计划中的每个槽位及其 `manifest.json`、`metrics.json`、`events.jsonl`、`trajectory.jsonl`，v2／v3还核对 `episode_start` 的精确初始状态与完整轨迹，保留当前结果状态和来源路径。只有**同一评分协议、完整标准计划且没有invalid**的模型组，才具备正式比较条件：v2要求65回合，v3要求70回合。存在不完整结果时展示状态和临时分，拒绝正式排名；v1、v2、v3之间均不能混排。

离线评分检查配置、成功条件、实际finish事件、事件末尾与metrics的一致性，以及相应协议要求的轨迹证据；它沿用运行时独立评测器的结果，不重新启动物理仿真，也不构成防篡改认证。旧v1计划的 `report`／`compare` 保留v1算法，不能用缺少后续协议证据的旧日志补出新版本排名。代码或环境指纹改变后不能直接续跑旧计划，需按目标协议建立新计划；原始结果继续保留。`--repeats 1`可用于v2的13回合或v3的14回合探索性检查，只产生临时分；正式排名要求5次重复。`run`使用Linux文件锁，当前入口面向本工作区的Linux／WSL环境。

## 9. 报告核验清单与结论边界

每份比较报告至少需要核对：

1. 模型标签、请求模型名、事件中实际返回的模型标识、运行日期、服务及推理配置；
2. 协议对应的13或14个任务、每任务5个重复、scene seed与唯一结果绑定，避免漏项、重复或挑选结果；
3. 任务文本、系统提示与工具schema、观测／动作／完成协议、代码和资产哈希；
4. 全部固定预算、近期历史策略、思考请求、当前图像窗口与仿真暂停模式；
5. 正式成功条件、最终停止和错误类型的一致性，不用模型文字声称替代独立评分；
6. 评分版本、60／20／10／5／5权重、路径采样及下界、分项与综合分，避免混用成功率和综合分；
7. 日志与原始结果完整性，未知成本字段及任何人工干预、重做或协议变更。

不同模型可使用不同服务，但不能向某个模型额外提供目标真值、旧成功轨迹、更多历史、专用任务提示或额外工具。评分文件和轨迹中的评测真值只供离线分析，不应被下一次模型请求当作允许观测。

5次重复是小样本，0/5和5/5都不足以证明稳定的泛化优劣。报告应给出每个场景的实际成功数及各组结果，避免只呈现总分或把很小的差距写成显著领先；未实际计算的置信区间和显著性不能编造。

v2／v3主分测的是各自固定场景、固定预算和预设权衡下的安全完成与运行效率。增加复合类后类别权重和任务范围都改变，不能把v3分数与既有v2的82.96分作直接优劣比较。不同权重可能改变排名，不能把一次综合排名当作所有应用偏好的结论。要比较提示、记忆、Task Agent或动作能力，应另立消融协议、同时计入新增调用与成本，不能把修改Harness带来的变化全部归因于大模型本身。
