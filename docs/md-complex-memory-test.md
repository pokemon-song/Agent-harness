# 用 MD 双 Agent 架构复测原复杂任务

这组实验将独立 Markdown 记忆 worker 接入原来的六阶段复杂任务。场景、订单生成和物理验收沿用 [原复杂任务](complex-memory-mission.md)，检验新架构在长导航期间能否形成可交班记忆，并完成多次交班、片段组合及有效订单修订。

它与 [短动作 MD demo](async-md-memory-demo.md) 分开记录，协议名为 `md-complex-memory-v1`，不进入旧模型排行榜。新旧实验的模型角色、提示词、调用预算、历史窗口和独立随机订单都有差异，即使本次成功，也不能直接得出“仅因采用双 Agent 就提高成功率”的因果结论。

## 实际分工

学习阶段的记忆 worker 使用独立模型实例，接收该班公告、公开图像与机器人执行反馈，自主选择 Markdown 路径、正文和修订方式。导航规划模型只接收本班物理巡检任务，通过检索和读取已经发布的 MD 获得记忆；程序不把完整公告再复制成另一条规划器答案通道。

规划器继续使用原机器人的公开观测、点测量和动作 Harness 完成导航。场景真值、私有合同、路线评分器与第三视角归档不作为模型输入。记忆来源、版本和处理水位受到检查，语义解释仍是模型决策，不能把证据引用有效等同于文字完全正确。

每一阶段结束后停止 worker、关闭模型与机器人，再由独立进程创建下一阶段。各阶段的世界与短期上下文真实重置，和短动作 demo 中连续世界内更换规划上下文的方式不同。记忆目录只在 worker 关闭后复制；程序不补写缺失的订单片段。

## 六个阶段

| 阶段 | 任务与记忆来源 | 记忆权限 |
| --- | --- | --- |
| `dispatch` | 原绕柜、穿绿门、接近 B；初始订单、旧目的地区域别名／通道、回执前半段 | 独立 worker 可写 |
| `fragments` | 交错箱体巡检；复制第一班实际 MD，加入后半段、别名映射和另一订单干扰 | 独立 worker 可写 |
| `revision` | 维护设备绕障巡检；复制第二班实际 MD，加入有效 R2 与后出现的 `ARCHIVED R1` | 独立 worker 可写 |
| `full` | 使用第三班后实际 MD，在多区地图按当前订单完成配送 | 只读 |
| `stale` | 使用第二班后实际 MD，在相同最终地图运行 | 只读 |
| `empty` | 同结构、同世界作用域空记忆，在相同最终地图运行 | 只读 |

最终回合不会启动写入记忆的 worker，也不向只读源目录补写新图像证据。运行前后核对整个目录内容；新帧和执行记录保存在该阶段自己的运行目录中。三个最终条件使用相同任务、模型设置、工具和物理起点，配对审计记录实际检查是否完成，缺失阶段不计为通过。

## 预算与复现命令

原物理任务的每阶段预算继续使用：

| 阶段 | 规划模型调用上限 | 回合墙钟上限 | 仿真上限 |
| --- | ---: | ---: | ---: |
| `dispatch` | 40 | 900 秒 | 150 秒 |
| `fragments` | 30 | 900 秒 | 150 秒 |
| `revision` | 30 | 900 秒 | 150 秒 |
| `full`、`stale`、`empty`，每个条件 | 60 | 1,200 秒 | 240 秒 |

每个学习阶段另外允许记忆 worker 最多 12 次模型调用，三个最终条件的记忆 worker 调用数为 0。因此默认完整六阶段最多尝试 **280 次规划请求加 36 次记忆请求，共 316 次**；不是旧实验的 280 次总请求预算。独立角色的调用和用量分别记录，不能只统计规划器而漏记后台成本。

默认使用 `deepseek-flash`，单次 API 时限 180 秒，输出上限 16,384 tokens，两个角色各自保留最近 2 轮历史；原单 Agent 增额实验使用 6 轮历史。没有自动重跑整个实验或替模型补答案。回合到时、模型异常、执行失败和未处理事件分别保留。

```bash
# 查看参数，不调用模型
.venv/bin/python scripts/run_md_complex_memory_mission.py --help

# 真实模型 + Go2/MuJoCo；创建独立实验目录，默认保存控制步状态
MUJOCO_GL=egl .venv/bin/python scripts/run_md_complex_memory_mission.py \
  --api-key-file ../deepseekapi.txt \
  --api-timeout 180 --max-output-tokens 16384 --memory-calls 12

# 完成后渲染已执行阶段的连续第三视角视频
MUJOCO_GL=egl .venv/bin/python scripts/render_complex_memory_video.py runs/<本轮目录>

# 离线生成新架构专用报告与播放页
.venv/bin/python scripts/report_md_complex_memory.py runs/<本轮目录>
```

报告脚本只读原始工件，不请求模型、不重新仿真。已有 `REPORT.zh-CN.md`、`analysis.json` 或 `watch.html` 时拒绝覆盖；应先渲染视频，再生成报告。未渲染时只展示真实公开观测帧，并明确标注为离散截图。

## 工件与评分

每轮创建 `runs/<时间>-md-complex-memory-<ID>/`。`experiment.json` 冻结源文件、提示词、Git、随机合同哈希和所有预算。`summary.json` 保留已运行阶段、未运行条件、停止原因以及两个角色的请求和已知用量。

各阶段目录包含 `events.jsonl`、`metrics.json`、`worker.json`、`memory-agent.jsonl`（仅写入阶段）、`memory-initial.json`、`memory-final.json`、真实轨迹和前视帧；实际产生哪些工件取决于是否完成启动与运行。`memory/<phase>/` 包含该阶段的事件账本、公开证据和不可变 MD 版本。终局只读副本与来源目录分别核对，不能从程序初始化的目录存在推断模型保存了语义记忆。

新报告按两个模型角色统计请求数、完整回复数、已知 token、用量缺失和工具失败；按实际发布清单链接 MD 版本，并记录规划器真正读取的文档。旧接口 `memory_save` 的调用数不用于衡量这次异步 MD 写入。

主任务通过仍要求三个学习阶段和 `full` 最终配送全部严格通过。最终验收继续检查物理到达、停止、碰撞／跌倒、有效修订、目的地、完整六位回执、声明通道与实际过门顺序。`stale` 的任意失败不自动证明采用了过期订单；`empty` 未运行也不算空记忆对照通过。本组不自动授予记忆收益或修订收益结论，需结合完整对照、实际读取和回执证据解释。

当某阶段没有发布可交班 Markdown，后续依赖阶段停止。要进入最终对照，还要求来源记忆没有未处理的关键事件。一个学习阶段发生导航失败但保留下来的记忆仍可用于后续诊断时，完整主任务结果仍为失败，不能把诊断回合成功替代整体任务成功。

## 录像与结果边界

第三视角来源于各阶段真实 Go2 控制步状态，以离线 `mj_setState + mj_forward` 重建，不补跑成功轨迹。默认 `mission-third-person-motion.mp4` 按仿真时间播放，模型等待压缩；真实墙钟耗时另列。不同阶段之间 RESET 卡表示实际重建进程和机器人世界，未运行阶段不会生成虚构画面。

这次依然是模型推理期间暂停物理仿真的 Go2 实验。记忆 worker 的异步调用并不提供现实机器人实时抢占、动态障碍预测或急停保障。自由文本可能重复、漏写、误解图像或提出不必要的动作建议；来源和版本门控能限制传播范围，但尚未完整核验 MD 语义。

代码、报告和原始模型产物分别保留，不人工修正文档后再计为模型成功。本轮不推送 GitHub。

## 2026-11-10 实测结果

运行目录：[20261110-202117-md-complex-memory-27b735](../runs/20261110-202117-md-complex-memory-27b735/)。运行冻结在干净提交 `02d3460`、版本 `0.5.0.dev2`，实际调用 DeepSeek，实际执行 Go2/MuJoCo。结果为 **第一班巡检通过，完整任务失败**，没有自动重跑。

| 阶段 | 结果 | 墙钟秒 | 仿真秒 | 路径米 | 规划／记忆请求 |
| --- | --- | ---: | ---: | ---: | ---: |
| dispatch | 三阶段均通过，正常 finish | 577.02 | 47.42 | 5.980 | 33 / 12 |
| fragments | 初始关键记忆不可用；第 2 次记忆请求传输错误 | 47.52 | 0.60 | 0.009 | 0 / 2 |
| revision | 初始关键记忆不可用；第 3 次记忆请求超时 | 221.06 | 0.60 | 0.009 | 0 / 3 |
| full / stale / empty | 未运行，关键公告仍未处理 | — | — | — | 0 / 0 |

第二、三班的 0.60 秒和约 9 毫米轨迹是最终停车时的仿真／站姿漂移，没有执行任务导航。第一班独立评分确认绕柜、正确穿门、门后 0.8 米余量及接近 B 的顺序；终点距 B 中心 1.076 米、距离误差 0.076 米，停稳且无碰撞、跌倒。

总计 **50 次请求，48 次完整回复，已知 1,163,840 tokens**：规划器 33 次、456,904 tokens，记忆 Agent 17 次、706,936 已知 tokens。另两次失败请求没有完整用量，不能当成零计费。已执行阶段墙钟合计约 845.60 秒，不含进程启动及离线渲染。不同角色成本全部计入，新旧历史窗口、提示词、随机订单与角色划分均不同，不能由单次结果推导架构因果收益。

本轮发现：

1. **及时保存有进展，但交班积压没有解决。** 第一条规划请求前已有 MD v1，第一班总共发布 4 个版本；记忆调用预算耗尽时只处理到事件 seq 18，留下 16 条反馈。第二班追加 seq 35 公告、第三班追加 seq 36 公告，两班模型始终处理旧反馈 seq 19–26，尚未看到新公告即发生错误。因此不能把后两班失败解释为模型无法合并片段／理解修订。
2. **工具约束没有完整公开。** `world/` 三次被路径白名单拒绝，schema 却未说明完整可用目录，错误回包仅提供代码；每批短期历史又重新开始。一次双工具调用被拒，一次正文 6,474 字符超过已声明的 6,000 上限。第一班这 5 条被拒回复耗用已知 264,043 tokens（双工具回复含两个失败结果）。
3. **自由文本更新存在信息退化。** v1 正文保留完整订单 ID，v2/v3 将其歪写为 `ord` 形式，v4 正文省略该标识；正确 ID 仍存在于 Harness 的 scope 和原始公告，不能说数据库全部丢失。v4 还因机器人反馈没有佐证，把明确 ACTIVE 的调度指令描述为未验证转述。MD 发布成功与引用有效不能代替语义正确性。
4. **直接中断来自两种 API 故障。** 第二班错误为 `MODEL_TRANSPORT_ERROR`，该请求约 37.50 秒；第三班为 `MODEL_TIMEOUT`，该请求约 180.09 秒。公开错误记录不足以进一步判定网络或服务端根因。关键事件未处理时阻止动作的门控生效，后续完整／旧版／空记忆对照均未运行。

优先改进方向是公开准确的路径／长度契约并返回字段级错误、控制普通反馈积压并让关键公告及时被处理、加强模型对订单身份与有效指令的保留。这里仅记录诊断，没有中途修改冻结代码、补写模型答案或提高预算重跑。
