# 跨班次长期记忆任务：巡检、交班与交付

本文件说明新增任务的设计与验收边界，**尚不报告实际测试结果**。本轮目标版本为 `0.3.0`，开发分支为 `feature/long-memory-mission`，暂不推送 GitHub；最终提交与标签以实际仓库记录为准。

任务评估信息能否通过持久记忆跨越一次完整交班。班次之间会关闭进程、重建模型客户端与机器人后端，并重置世界和机器人起点。它覆盖跨回合的记忆保存与复用，尚不覆盖连续未重置世界中的长时间控制。

## 任务过程

| 阶段 | 模型可获得的信息 | 要完成的事 |
| --- | --- | --- |
| 第一班次 `briefing` | 当前巡检任务、公开观测，以及包含订单号、随机交付目的地和6位回执码的订单 | 在真实 MuJoCo 中完成复合巡检，并自行决定如何用记忆工具保存下一班次需要的信息 |
| 交班 | 关闭本班次进程，归档持久记忆 | 丢弃模型客户端、MemoryAgent、Harness、机器人后端、近期历史、私有思考状态和 RAM 工作笔记 |
| 第二班次 `with_memory` | 新的固定 A/B/C 交付世界、公开观测、订单号、第一班次记忆库的只读副本 | 自主检索和读取经验，前往正确标牌、提交交付信息并停稳完成 |
| 第二班次 `empty_memory` | 同一交付世界、起点、订单号和工具，但持久库为空且只读 | 在同样预算下完成同一交付任务，作为缺少交班内容的对照 |

第一班次的复合巡检仍是 `composite_drawers_gate_b`：绕过抽屉柜、从绿色矩形门开口穿过并完成门后余量，最后接近 B 停稳。本班次巡检的对象固定为 B；订单中的 A/B/C 目的地属于下一班次，不改变本班次巡检目标。原有复合场景规则见 [composite-tests.md](composite-tests.md)。

订单目的地从 A/B/C 中独立随机选择，回执码是保留前导零的6位字符串。订单内容与场景 seed、机器人初始位置独立。订单在第一班次任务文字中持续可见，直到交班；不应将它描述成仅出现一次的单帧提示。

模型必须自行通过记忆工具保存内容，程序不把正确目的地或回执码预填进库，也不在模型遗漏或记错时补写答案。非空记忆归档只表示有可交班内容，不能自动证明本订单被完整、正确地记住。

只有第一班次归档记忆非空且没有基础设施错误，才启动两个交付分支。如果第一班次物理巡检失败，但已留下可读取记忆且没有基础设施错误，仍可执行后续分支做诊断；此时整段任务不能算成功。模型未保存记忆时如实停止，不补答案或另抽订单掩盖结果。

## 重置与对照条件

三个回合分别在独立子进程运行。第二班次不能复用第一班次的模型对象、消息历史、工具结果缓存、跟踪点、局部里程计、工作笔记或机器人状态。新工作笔记从空白开始，模型可在当前回合重新写入。

交付世界始终生成同一组 A/B/C 标牌，起点与场景配置相同。正确目的地只指定给独立 evaluator，不控制哪些标牌出现，也不产生提示正确答案的颜色、装饰或可见布局变化。

两组交付使用同一隐藏订单、模型配置、提示词、公开任务、工具集合和预算，均为 `read_only`。`with_memory` 读取交班库副本；`empty_memory` 使用预先创建的空库，具有同样的数据库结构和机器人配置作用域。空库不是关闭记忆工具的 `off` 模式。

两组的实验条件差异限于 SQLite 内容及其派生的条目计数、检索结果与读取内容。条件名称和日志路径只用于审计，不应进入模型任务文字。副本、空库及原始交班库分别保存；原始交班库不能被交付分支改写。工作笔记是当前回合的 RAM 状态，两组都可更新，均不写入持久库。

## 提交与独立验收

新增工具为：

```text
submit_delivery(order_id, destination, receipt_code)
```

`destination` 为 A/B/C，`receipt_code` 为6位字符串。每个交付回合只有一次提交机会；幂等重放不能变成新的提交。工具只校验格式并记录提交，不反馈目的地或回执码是否正确，不返回正确答案，也不能用反复提交探测答案。

工具回包表示提交已记录，不表示任务已成功。模型仍须通过正常完成流程停稳并调用 `finish`。最终独立验收同时检查：

- 物理到达与朝向满足正确交付标牌的公开验收要求，最终停稳，全程没有碰撞或跌倒。
- 已记录的订单号与本订单一致，提交的目的地与隐藏订单一致。
- 提交的回执码与隐藏回执精确一致，包括前导零。
- 正常完成声明已执行，且没有超过本回合的模型调用、墙钟和仿真预算。

提交结果和私有 evaluator 的判定只在回合结束后用于归档与评分，不作为下一轮模型观测或工具反馈。即使文本目的地与码正确，去错标牌或物理验收失败仍不能通过；即使机器人停在正确位置，未提交或回执错误也不能通过。

整段 `mission_success` 必须同时满足第一班次巡检成功和 `with_memory` 交付成功。`empty_memory` 是对照结果，单独报告；不要求它失败才能记录主任务成功，也不能因为它碰巧成功就重抽订单。

## 不泄漏答案的要求

第二班次的公开任务只提供 `order_id`，不提供正确目的地、回执码或第一班次任务全文。订单号必须与答案独立，不能编码目的地或回执，也不能采用带答案的默认命名。

以下内容不能绕过记忆工具直接传给第二班次模型：

- 第一班次原始日志、消息历史、私有思考、快照全文或已经整理好的答案摘要。
- 独立 evaluator 的目标真值、提交正确性、订单答案或最终评分。
- 指向正确目标的隐藏坐标、特有视觉标记，或含答案的提示词、文件名、条件名称与错误消息。

`with_memory` 经 `memory_search`／`memory_read` 取得模型先前保存的教训及其公开来源证据，属于预期的交班渠道。记忆文本仍是待核对的数据，不成为系统指令；有证据引用也不保证模型总结的每句话都正确。`empty_memory` 没有这份交班内容，但保留相同记忆工具和单次提交约束。

实现验证应检查：切换隐藏目的地或回执时，第二班次的初始世界图像、公开任务、工具和验收说明不随答案变化；对格式合规但答案不同的提交，在线回包不泄漏正确性。两组首次请求均不携带第一班次历史或工作笔记。

## 冻结预算与运行命令

| 回合 | 记忆模式 | 模型调用上限 | 墙钟上限 | 仿真上限 |
| --- | --- | ---: | ---: | ---: |
| `briefing` | `read_write` | 40 | 900秒 | 120秒 |
| `with_memory` | `read_only`，交班库副本 | 30 | 450秒 | 120秒 |
| `empty_memory` | `read_only`，预创建空库 | 30 | 450秒 | 120秒 |

共同设置为：seed=0、近期完整工具历史6轮、单次 API 超时90秒、输出上限8192 token（含思考）。记忆操作、交付提交和机器人动作都占普通模型决策轮次，没有额外的免费模型调用。每个回合独立受预算约束，启动后不扩额。

三回合最多合计100次模型调用，墙钟额度相加为1800秒；实际整段耗时还包含进程启动、初始化与归档，不能据此承诺恰好30分钟结束。仿真时间分别统计，不能把重置后的轨迹拼成一次连续世界运行。

查看参数不会运行实验：

```bash
.venv/bin/python scripts/run_long_memory_mission.py --help
```

下面的命令会启动真实模型 API 与 MuJoCo，产生实际费用；本文件不声称已经执行：

```bash
.venv/bin/python scripts/run_long_memory_mission.py

# 指定新的日志父目录和已有凭据文件
.venv/bin/python scripts/run_long_memory_mission.py \
  --runs-dir runs/long-memory-mission \
  --api-key-file ../deepseekapi.txt
```

驱动应在首次请求前冻结订单、预算、模型与思考协议、源码和提示词哈希、资产及 Git 版本信息。订单答案属于私有验收输入，须与模型可见上下文隔离。每次创建新实验目录，保留原始产物；没有 GitHub 推送步骤。

## 应报告的结果与局限

报告逐回合列出物理巡检／交付结果、正常完成与终止类型、预算使用、碰撞／跌倒和停稳状态。第一班次另外列出三阶段验收和记忆是否成功归档；两个交付分支另外列出是否提交、目的地判定、回执判定与最终联合成功。

同时保留模型请求数、记忆各工具的请求与执行状态、实际读取的条目 ID／版本、工作笔记状态、数据库初末逻辑快照哈希及只读完整性核对。资源报告包括墙钟、仿真时间、实际二维轨迹长度、已知 token 用量与完整度；缺失用量不能当作零费用。

应提供各回合的配置、公开工具事件、私有最终验收结果和原始图像路径，并明确区分模型看到的公开证据与事后评分真值。不输出私有思考文本，不把预定动作的接口测试计为真实模型成功。

本任务是新的记忆实验，不进入原 `go2-model-eval-v2`／`v3` 榜单，也不改写既有成绩。一次订单、一个固定场景和每条件一次运行只能形成案例观察。独立随机回执使无交班内容时难以可靠推断答案，但空库仍可能偶然猜中；不能声称绝对不可能、统计显著或一般长期能力已经得到证明。后续需要预先冻结多个独立订单与配对条件，控制运行顺序和服务波动，完整保留失败、无效与未完成样本。
